# xmldsig corpus

Shared corpus for response XML-DSig verification. The generator checks every case with the Rust core of the node (`internal/corewasm`, export `signature_report`). The Rust tests of the guest code (`core/src/gen4/x509`, `core/src/gen4/xmldsig`) must give each result exactly.

Generated by `internal/contract/cmd/genxmldsig` in amantrue-node. Do not edit by hand. The generator writes this corpus into a checkout of the amantrue-test-vectors repository (`xmldsig`). This repository holds the only copy. amantrue-node (`VECTORS_VERSION`) and amantrue-zk-node (`FIXTURES_VERSION`) fetch a pinned commit of it. Regenerate and check with:

```bash
cd amantrue-node
go run -tags amantrue_xml ./internal/contract/cmd/genxmldsig
AMANTRUE_ZK_FIXTURES=../amantrue-test-vectors go test -tags amantrue_xml ./internal/corewasm/ ./internal/contract/cmd/genxmldsig/
```

Commit and push the change in amantrue-test-vectors. Then write the new commit id into `VECTORS_VERSION` in amantrue-node and into `FIXTURES_VERSION` in amantrue-zk-node.

Regeneration is reproducible: the keys are the committed PKCS#8 PEM files in `internal/contract/cmd/genxmldsig/testkeys`, serial numbers are derived from each certificate's subject, issuer and key, validity times are fixed, ECDSA signatures are RFC 6979 deterministic, and RSA-PSS salts are derived from the signed bytes. `go test ./internal/contract/cmd/genxmldsig/` regenerates the corpus twice and requires both runs to equal the committed tree byte for byte. `-mint-keys` creates a key that a new case names and that does not exist yet; the generator refuses unused key files. The generator refuses to write a case whose core result differs from the case's declared expectation, so `expected.json` is the case's intent, checked once by the core at generation time and then by the Rust tests.

## Layout

Each case is `<group>/<case>/` with:

- `response.xml`: raw response bytes;
- `binding.json`: the binding's JCS bytes (`binding@1` with `extensions.signed_parts`), compiled from `testdata/secure-patient/SecurePatientService.wsdl` (or a variant, see below);
- `hints.json`: `[["<id>", <offset>], ...]` from the core export `signature_hints` unless the case says otherwise;
- `context.json`: `{"collector_created": <unix seconds>, "request_message_id": "<id or empty>", "request_auth": "<summary>"}`;
- `expected.json`: `{"ok": true, "signer": {...}}` or `{"ok": false, "error": "<exact error string>"}`. An ok case of the `relates` group also has `"relates_to": "<text of the signed wsa:RelatesTo>"`.

Defaults: collector created `2026-10-02T12:00:00Z`, Timestamp Created `2026-10-02T11:59:30Z` and Expires `2026-10-02T12:04:30Z`, certificates valid 2026-01-01 to 2036-01-01, binding `require [payload, timestamp]`, rows all, algorithms `[ecdsa-p256-sha256, rsa-pss-sha256, rsa-sha256]`, digests `[sha256]`, `relates_to true`, `max_chain 3`, anchor Demo Root. The default response is SOAP 1.1 with BSTs for the leaf (`cert`, first) and Demo Intermediate (`ca`), RelatesTo 2005/08 equal to the context message id, and references to the Timestamp, Body and RelatesTo.

Contract variants: `typed` adds `VipPatient` (an extension of `Patient`), so the compiled rows carry `xsi_type` steps on `tns:Patient`; `soap12` binds the port with the WSDL SOAP 1.2 binding namespace. Cases whose note says "binding edited" change the compiled binding before its JCS is taken.

Ruling C7: the four `interop/` cases are layout-equivalent, hand-authored from the published layouts of WSS4J/CXF, WCF and Metro, and signed by our own signer. Replace each with a captured message under the same name when one is available.

Consumer constraints: every BST in `chain/` and `basic/` parses under the shared certificate profile, the leaf is the first BST, and the chain is judged at `2026-10-02T11:59:30Z` (Task 15's harness relies on this). Certificates that the profile refuses live in `profile/`.

Attachment vectors (`attachments/`, spec 3): the binding is hand-built (documents, legacy SwA or part-name report contracts) with `extensions.attachments` and `extensions.signed_parts`, and the inputs are the guest's split form. `response.xml` is the root part as carried on the wire (`xop:Include` unexpanded); `content_type.txt` is the signed outer Content-Type; `manifest.txt` is the signed `Amantrue-Response-Parts` value (empty for a plain response); `supplied.json` is `[{"cid": "<content-id>", "file": "part-<n>.bin"}, ...]`, the attachment bytes the prover supplies (the core export `required_parts` unless the case says otherwise). The judge is the core export `signature_report` on the split form, with no walker hints. MTOM vectors are signed over the infoset first and optimized second (WSS4J, WCF); `hints.json` is computed on the root part. These cases are not walked by the row walker list below.

The node's `Signature-Input` reader vectors are node-only and live in the amantrue-test-vectors repository (`node/signature-input.json`; the generator writes them, flag `-siginput`); they are not part of this shared corpus.

## Bindings `contract.Compile` would not produce

These cases edit the compiled binding before its JCS is taken. Each binding still passes `binding.Decode`, which the guest's `load_v4` mirrors, so they are guest-hardening vectors: `load_v4` must accept them and the verifier must reach the rule they pin.

- `locate/binding-without-signed-parts`: binding edited: signed_parts removed
- `locate/binding-without-soap`: binding edited: the soap section removed
- `coverage/header-row`: binding edited: a row whose first step is soap:Header
- `coverage/encoded-needs-body`: binding edited to soap.use encoded; only the payload element is referenced, so the Body (multi-ref targets) is not covered
- `xsitype/wildcard-step-reads-every-element`: binding edited: the xsi_type steps use el "*", so Gender's xsi:type="xsd:string" is read and xsd is declared outside the Body
- `xsitype/wildcard-xmlns-empty-visible`: binding edited to wildcard xsi_type steps; an unprefixed Patient declares xmlns="" and carries xsi:type="VipPatient" (its own unprefixed name uses the default namespace)

## Verifier-only vectors

The bound-row walker refuses these responses: the core export `evaluate_sample` (document checks) or `conform` (every binding row walked) on the binding without `signed_parts` reports a document, value or xsi:type refusal. In the proving pipeline the walker runs first, so these vectors pin the signature verification only and are not proving inputs. A SOAP Fault body is not listed: the fault status rule, not the row walker, decides it.

- `locate/soap12-envelope-for-soap11-binding`: xml: document element {http://www.w3.org/2003/05/soap-envelope}Envelope is not a SOAP 1.1 Envelope
- `locate/second-body`: xml: Envelope has more than one Body
- `locate/body-empty`: xml: Body is empty
- `locate/body-text-only`: xml: Body is empty
- `locate/not-well-formed`: xml: malformed document
- `locate/binding-without-soap`: xml: payload is {http://schemas.xmlsoap.org/soap/envelope/}Envelope, binding expects {urn:amantrue:demo:patient}GetPatientResponse
